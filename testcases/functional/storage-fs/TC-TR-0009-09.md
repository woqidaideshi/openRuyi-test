# TC-TR-0009-09 ｜ 升级数据一致性

| 字段 | 值 |
|---|---|
| 关联需求 | TR-0009（存储与文件系统功能） |
| 测试类型 | 功能测试 |
| 功能模块 | 存储与文件系统 |
| 优先级 | P1 |
| 覆盖设备 | KVM/物理机 |
| 可自动化 | 是 |
| 自动化覆盖 | 否 |

## 描述

验证就地升级路径下，升级前已持久化的文件内容、目录结构及承诺保留的属性保持一致，重启后正常进入新版本，无非预期数据丢失或损坏。

## 前置条件

1. 已明确本次升级的目标版本（`dnf upgrade` 应能从当前版本到达该版本）。
2. 存在受支持的升级路径与可用升级源。
3. **必须在可一次性占用、允许重启的专用测试机（或虚拟机快照）上执行**；不要在多人共用或验证其他用例的机器上执行 `dnf upgrade`，否则会破坏环境、导致其他用例结论失效。
4. 执行前建议备份关键数据并确认可回滚（如虚拟机快照）。

## 测试步骤

1. 在 `/home`、`/etc`、`/var` 准备持久化测试数据（含多层目录、链接、非默认权限与 root 属主文件）：
   ```bash
   CASE_TMP=/var/tmp/tc-upgrade && rm -rf $CASE_TMP && mkdir -p $CASE_TMP
   mkdir -p /home/openruyi/tc-data/sub/deep
   echo "home-data" > /home/openruyi/tc-data/file.txt
   echo "deep-data" > /home/openruyi/tc-data/sub/deep/nested.txt
   ln -s file.txt /home/openruyi/tc-data/link.txt
   ln /home/openruyi/tc-data/file.txt /home/openruyi/tc-data/hard.txt
   chmod 640 /home/openruyi/tc-data/file.txt
   sudo mkdir -p /var/tc-data && sudo chown openruyi /var/tc-data
   echo "var-data" > /var/tc-data/file.txt
   sudo sh -c 'echo "root-data" > /var/tc-data/rootfile.txt'
   sudo sh -c 'echo "etc-data" > /etc/tc-marker.conf'
   ```
2. 记录基线：升级前版本、启动标识、内容 md5 与属性清单（权限位、属主、属组、类型、符号链接指向）：
   ```bash
   uname -r > $CASE_TMP/before.version
   grep -E '^(PRETTY_NAME|VERSION_ID|VERSION)=' /etc/os-release >> $CASE_TMP/before.version
   cat /proc/sys/kernel/random/boot_id > $CASE_TMP/before.bootid
   find /home/openruyi/tc-data /var/tc-data /etc/tc-marker.conf -type f -exec md5sum {} + | sort -k2 > $CASE_TMP/before.md5
   find /home/openruyi/tc-data /var/tc-data /etc/tc-marker.conf -printf '%m %u %g %y %p -> %l\n' | sort -k5 > $CASE_TMP/before.attr
   cat $CASE_TMP/before.version
   echo "boot_id: $(cat $CASE_TMP/before.bootid)"
   ```
3. 执行受支持的就地升级（如全量升级）：
   ```bash
   sudo dnf upgrade -y
   ```
4. 重启并确认版本：

   执行重启，该操作会中断当前会话：
   ```bash
   sudo reboot
   ```

   重启后重新接入，执行：
   ```bash
   cat /proc/sys/kernel/random/boot_id > $CASE_TMP/after.bootid
   echo "boot_id before=$(cat $CASE_TMP/before.bootid) after=$(cat $CASE_TMP/after.bootid)"
   [ "$(cat $CASE_TMP/after.bootid)" != "$(cat $CASE_TMP/before.bootid)" ]
   echo "bootid-changed:$?"
   uname -a
   head -5 /etc/os-release
   ```
5. 比对持久化数据的内容与属性：
   ```bash
   find /home/openruyi/tc-data /var/tc-data /etc/tc-marker.conf -type f -exec md5sum {} + | sort -k2 > $CASE_TMP/after.md5
   diff $CASE_TMP/before.md5 $CASE_TMP/after.md5; echo "md5-diff:$?"
   find /home/openruyi/tc-data /var/tc-data /etc/tc-marker.conf -printf '%m %u %g %y %p -> %l\n' | sort -k5 > $CASE_TMP/after.attr
   diff $CASE_TMP/before.attr $CASE_TMP/after.attr; echo "attr-diff:$?"
   ```
6. 核对 `/etc` 配置文件的升级保留情况：
   ```bash
   sudo find /etc -maxdepth 2 \( -name '*.rpmnew' -o -name '*.rpmsave' \) | sort
   ls -l /etc/tc-marker.conf
   ```
7. 扫描内核与文件系统告警：
   ```bash
   sudo dmesg -l err | tail -20
   sudo journalctl -b -p err --no-pager | tail -20
   sudo dmesg | grep -icE 'EXT4-fs error|XFS.*corrupt|I/O error'
   ```
8. 清理：
   ```bash
   rm -rf /home/openruyi/tc-data $CASE_TMP
   sudo rm -rf /var/tc-data
   sudo rm -f /etc/tc-marker.conf
   ```

## 预期结果

1. 步骤 1：测试数据创建成功，同时包含多层目录、符号链接、硬链接、非默认权限位（`640`）与 `root` 属主文件。
2. 步骤 2：基线包含升级前版本（`uname -r` 及 `os-release` 的 `PRETTY_NAME`/`VERSION_ID`）、启动标识（`before.bootid`）、`before.md5` 与 `before.attr`；`before.attr` 覆盖所有目录、普通文件与符号链接，含权限位、属主、属组、类型及链接指向。
3. 步骤 3：升级完成，退出码为 0。
4. 步骤 4：
   - `bootid-changed` 退出码为 `0`（`after.bootid` 与 `before.bootid` 不同，确认系统确实重启）；
   - `uname -r` 与 `/etc/os-release` 显示的版本与步骤 2 记录的升级前版本不同，且已达目标版本；
   - 系统正常启动，可正常登录。
5. 步骤 5：`md5-diff` 与 `attr-diff` 均无输出、退出码均为 0（文件内容、目录结构、权限位、属主、符号链接指向全部保持一致）。
6. 步骤 6：
   - 不出现 `*.rpmsave`（用户内容未被覆盖后丢弃）；
   - 若出现 `*.rpmnew`，说明该包的配置文件被升级保留为新文件、原文件未被覆盖，属预期保留行为，需在报告中记录清单；
   - `/etc/tc-marker.conf` 的内容与属性不变。
7. 步骤 7：
   - `grep -c` 命中数为 `0`（无 `EXT4-fs error` / `XFS` 损坏 / `I/O error` 类告警）；
   - `dmesg -l err` 中无本次升级引入的存储相关错误，其余条目逐条确认为既有噪声（如该机型已知的 `sophgo-dwmac ... cannot attach to PHY`）；
   - `journalctl -b -p err` 中无本次升级引入的存储相关错误，其余条目逐条确认为既有噪声。
8. 步骤 8：清理完毕。

## 实测记录

| 项目 | 实测值 |
|---|---|
| 基线规模 | 步骤 1/2 实测生成 `before.md5` 6 条（`file.txt` 与硬链接 `hard.txt` md5 相同）、`before.attr` 11 条，正确体现 `640` 权限位、`root` 属主文件与符号链接指向 |
| 清单命令 | 已在 openRuyi riscv64 验证：`find -printf '%m %u %g %y %p -> %l\n'` 可输出如 `644 openruyi openruyi f /path/a.txt -> ` 与 `777 openruyi openruyi l /path/lnk -> sub/a.txt`，覆盖属主与链接指向 |
| 比对命令 | 未发生变更时 `diff before.md5 after.md5` 与 `diff before.attr after.attr` 退出码均为 0，可作为判定基线 |
| 告警扫描 | `dmesg -l err` 与 `journalctl -b -p err` 可正常读取；文件系统错误关键字命中数为 `0` |
| 已知噪声 | ① 该机型 `sophgo-dwmac ... cannot attach to PHY (error: -ENODEV)` 为已知网卡告警；② 同机执行过 NFS/CIFS 用例会留下 `CIFS: VFS: ... failed to create a new SMB session` / `cifs_mount failed w/return code = -13` 等条目。两者均不属存储数据损坏，不应计为本用例失败，但需在报告中说明来源 |
| 重启判据 | **不能用 `/proc/stat` 的 `btime` 判断是否重启**：实测重启后 `btime` 反而变小（`1786451035` < 重启前 `1794196236`）。原因是该机 RTC 为 `2026-06-23`、`timedatectl` 显示 `System clock synchronized: no`，而 `btime` 由墙钟推导，时钟被步进即重算。改用 `/proc/sys/kernel/random/boot_id`（每次启动唯一，实测重启前后由 `38f33a3a…` 变为 `f8e3e2e1…`）。该机无 `uptime` 命令，`who -b` / `last` 输出亦陈旧（`Aug 11 08:24`），均不可用 |
| 临时目录位置 | 实测 `/` 为 `/dev/nvme0n1p2`（xfs），`/var`、`/var/tmp` 均位于该持久化分区，重启后数据保留；`/tmp` 为 `tmpfs /tmp tmpfs rw,noatime`，重启即清空。`tmpfiles.d/tmp.conf` 对 `/var/tmp` 的清理规则为 `q /var/tmp 1777 root root 30d`（按 30 天文件年龄，非按重启），不影响本用例；故 `CASE_TMP` 置于 `/var/tmp/tc-upgrade` |
| 自动化前提 | 步骤 1～8 均为命令 + 退出码判定，可直接脚本化；唯一步骤 4 需夹具层支持“发出重启 → 等待主机恢复 → 新会话续跑”，单进程脚本无法自持。另 `dnf upgrade` 不可回滚，自动化执行须在一次性虚拟机或快照上进行 |
| 升级与重启 | 本条未执行 `dnf upgrade` 与重启（需允许重启的专用机器或快照）；步骤 1、2、5、6、7、8 的命令与判定均已实测，升级后的版本与重启相关结论待专用环境回填 |
