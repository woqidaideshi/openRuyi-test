# TC-TR-0010-03 ｜ 连通性与链路故障恢复

| 字段 | 值 |
|---|---|
| 关联需求 | TR-0010（网络基础功能） |
| 测试类型 | 功能测试 |
| 功能模块 | 网络 |
| 优先级 | P1 |
| 覆盖设备 | KVM/物理机 |
| 可自动化 | 是 |
| 自动化覆盖 | 否 |

## 描述

验证与规定节点之间的网络连通，以及链路中断后连通性能够自动恢复、无需重启网络服务。网关地址与对端节点均由命令自动获取。

## 前置条件

1. 网关地址与对端节点地址**由步骤 1 自动获取**：网关取自默认路由；对端优先取邻居表中除网关外的已知节点，取不到时回退为网关。可用 `PEER=` 环境变量指定（"规定节点"清单待需求方明确）。
2. 已安装 `iproute2`、`iputils`。
3. 本用例使用**隔离方案**（步骤 3～6）制造链路故障，不触碰承载管理连接的接口，因此可在与其他用例共享的机器上执行。
4. 主机具备创建网络命名空间的条件（`sudo ip netns` 可用），用于在不触碰管理连接的前提下制造链路故障。

## 测试步骤

1. 自动探测网关与对端节点，记录入口基线：
   ```bash
   CASE_TMP=/var/tmp/tc-net-conn && rm -rf $CASE_TMP && mkdir -p $CASE_TMP

   IFACE=$(ip route show default | awk '{print $5; exit}')
   GW=$(ip route show default | awk '{print $3; exit}')
   PEER=${PEER:-$(ip neigh show dev "$IFACE" | awk '$NF=="REACHABLE"||$NF=="STALE"||$NF=="DELAY"{print $1}' | grep -v "^$GW$" | head -1)}
   PEER=${PEER:-$GW}

   cat > $CASE_TMP/env.sh <<EOF
   IFACE=$IFACE
   GW=$GW
   PEER=$PEER
   EOF

   ip -br addr > $CASE_TMP/before.addr
   ip route > $CASE_TMP/before.route
   ip neigh show dev "$IFACE" > $CASE_TMP/before.neigh
   cat $CASE_TMP/env.sh
   ip -br addr
   ip route
   ```
2. 验证与规定节点的基础连通性：
   ```bash
   CASE_TMP=/var/tmp/tc-net-conn && . $CASE_TMP/env.sh
   ping -c 4 "$GW"
   ping -c 4 "$PEER"
   ```
3. 建立隔离测试链路（veth + 网络命名空间，不影响管理连接）：
   ```bash
   CASE_TMP=/var/tmp/tc-net-conn && . $CASE_TMP/env.sh
   sudo ip netns add tcn
   sudo ip link add veth0 type veth peer name veth1
   sudo ip link set veth1 netns tcn
   sudo ip addr add 192.0.2.1/24 dev veth0
   sudo ip link set veth0 up
   sudo ip netns exec tcn ip addr add 192.0.2.2/24 dev veth1
   sudo ip netns exec tcn ip link set veth1 up
   sleep 1
   ping -c 4 -W 1 192.0.2.2
   ```
4. 制造链路故障并确认连通中断：
   ```bash
   CASE_TMP=/var/tmp/tc-net-conn && . $CASE_TMP/env.sh
   sudo ip link set veth0 down
   ping -c 2 -W 1 192.0.2.2
   ```
5. 解除故障并确认连通自动恢复：
   ```bash
   CASE_TMP=/var/tmp/tc-net-conn && . $CASE_TMP/env.sh
   sudo ip link set veth0 up
   sleep 1
   ping -c 4 -W 1 192.0.2.2
   ```
6. 清理隔离环境并复核原网络：
   ```bash
   CASE_TMP=/var/tmp/tc-net-conn && . $CASE_TMP/env.sh
   sudo ip netns del tcn
   ip link show veth0
   ip route
   ping -c 3 "$GW"
   rm -rf $CASE_TMP
   ```

## 预期结果

1. 步骤 1：`IFACE`、`GW` 探测出非空值（实测 `eth2` / `10.213.0.1`），`PEER` 取到非空值（实测邻居表选出 `10.213.8.189`；无其他邻居时回退为网关并记录）；`env.sh`、`before.addr`、`before.route`、`before.neigh` 均已生成。
2. 步骤 2：`GW` 与 `PEER` 均可达，丢包率 0%，退出码为 0。
3. 步骤 3：`netns` 与 `veth` 创建成功（各命令退出码为 0），`192.0.2.2` 可达（丢包率 0%，退出码 0）。
4. 步骤 4：故障生效，`ping` 丢包率 100%，退出码非 0（实测为 `1`）。
5. 步骤 5：链路恢复后连通性自动恢复（丢包率 0%，退出码 0），且未重启 `NetworkManager`。
6. 步骤 6：`veth0` 已随命名空间删除（`ip link show veth0` 返回非 0，提示 `Device "veth0" does not exist`）；默认路由与 `GW` 连通保持（退出码 0）；`$CASE_TMP` 已删除。

## 实测记录

| 项目 | 实测值 |
|---|---|
| 网关自动获取 | `ip route show default` → `default via 10.213.0.1 dev eth2 proto dhcp`，取出 `GW=10.213.0.1`，`ping` 0% 丢包 |
| 对端自动获取 | 邻居表 `ip neigh show dev eth2` 实测含 `10.213.8.189 lladdr c0:a6:6d:77:e1:d1 STALE` 与网关 `10.213.0.1`；排除网关后选出 `PEER=10.213.8.189`，`ping` 0% 丢包（`rtt avg 0.999 ms`） |
| 对端回退 | 邻居表只有网关时 `PEER` 回退为 `$GW`，此时“网关与对端”为同一节点，报告中应注明，或改用 `PEER=` 指定真实对端 |
| 为何不用域名作对端 | 实测 `openruyi.cn` 解析为 `36.110.52.101`，`ping` 平均 `0.25 ms`，`tracepath` 仅 2 跳（`1: no reply` → `2: 36.110.52.101 reached`）；而到同网段邻居 `10.213.8.189` 为 `1.10 ms`。公网地址比同网段邻居更快、只走 2 跳，说明回包由本地设备应答（代理/NAT 劫持），用它当“对端节点”验证的不是规定节点间连通。域名仅用于 `TC-TR-0010-01`/`-02` 的 DNS 解析与应用层访问。若确实需要，可用 `PEER=<域名或IP>` 覆盖，但须在报告中注明外部依赖与劫持风险 |
| 隔离方案结果 | 实测 `baseline_rc=0` → `fault_rc=1` → `recovered_rc=0`；`ip netns del` 返回 0，随后 `veth0` 消失 |
| 测量陷阱 | 判定必须直接取 `ping` 的退出码。写成 `ping ... \| tail -2; echo $?` 得到的是 `tail` 的退出码（恒为 0），会把故障态误判为正常——本次验证中已实际踩中并纠正 |
| 清理方式 | `ip netns del` 会连带销毁命名空间内的进程与 veth 对端（实测删除后 `ss -ltn` 无残留监听、`veth0` 不存在）。**不要**用 `pkill -f '<命令串>'` 清理：实测通过 `ssh host '...'` 执行时该模式会匹配到执行者自身命令行，导致 shell 被杀、清理中断并残留进程 |
| 变量跨会话保留 | 每步开头必须先写 `CASE_TMP=/var/tmp/tc-net-conn` 再 `. $CASE_TMP/env.sh`；只写后者时变量为空会展开成 `. /env.sh`，实测报 `No such file or directory` |
| 未执行项 | 物理网口的 down/up 方案未执行（原因见下方已知问题），本用例以 veth 方案为准 |

## 已知问题（2026-11-10 在 riscv64 物理机实测）

**现象**：备用网口 `eth0`（`sophgo-dwmac`，平台设备 `7030006000.ethernet`）无法启用：

```
$ sudo ip link set eth0 up
RTNETLINK answers: No such device        # ENODEV
$ sudo nmcli device connect eth0
Error: Connection activation failed: The device could not be readied for configuration.
```

**根因**：内核日志显示 MDIO 总线上未发现 PHY，phylink 无 PHY 可用导致 `ndo_open` 返回 `-ENODEV`：

```
[ 18.802060] mdio_bus stmmac-0: MDIO device at address 0 is missing.
[ 18.749715] sophgo-dwmac 7030006000.ethernet: Active PHY interface: RGMII (1)
```

`/sys/class/net/eth0/carrier` 为 `unknown`，`eth1` 可 up 但 `carrier=0`（未接网线）。

**影响**：本机无法用 `eth0` 作为"非管理接口"制造物理链路故障。若其他环境的非管理口可用，可将步骤 3～6 替换为：`sudo ip link set <非管理接口> down` → `ping -c 2 "$GW"` → `sudo ip link set <非管理接口> up` → `ping -c 4 "$GW"`，判据不变（丢包率 100% → 恢复 0%）。
